# Плейбуки по стадиям

## Общий принцип

- Начинай с чтения существующих артефактов в `.madspec/<branch>/`, а не с предположений о текущем этапе.
- Перед реализацией сверяйся с `implementation-plan.md`, `steps/`, `memory/progress.json` и релевантным производным контекстом.
- Если работа идет через структурированную память, сначала обновляй память, потом пересобирай представления, потом проверяй результат.

## MVP-поток

Для MVP соблюдай порядок:

- `concept -> design -> tech -> architecture -> deploy -> plan -> implement`

### `mvp.concept`

- В обычных ходах диалога, когда контекст читает агент, используй краткий `madspec memory retrieve --toon-output`; `--json-output` оставляй для машинной обработки.
- При необходимости добавляй `--query` для смешанного поиска.
- `--include-history` включай только при явной необходимости.
- `--full-artifact` запрашивай только перед финальной валидацией, итоговым обзором и `checkpoint`.

### `mvp.design`

- Для `mvp.design` считай нормой длинную итеративную работу через много независимых чатов: новый чат должен восстанавливать состояние из `.madspec/<branch>/memory/`, `ui-design.md` и `ui-prototype/`, а не из истории предыдущего разговора.
- В начале каждой новой сессии выполняй `madspec memory retrieve --stage mvp.design --toon-output`.
- Если видно, что детерминированного контекста недостаточно, используй `--query` или `madspec memory search`.
- Затем сверяй `ui-design.md`, `.madspec/templates/ui-storyboard-contract.md` и файлы в `ui-prototype/`.
- Не считай дизайн завершенным, пока пользователь явно не утвердил текущее состояние.
- При проектировании интерфейса, сценариев и HTML/CSS-прототипов обязательно подключай навык `frontend-design` как основной; `ui-storyboard-contract` задает структуру и порядок проверки, а `frontend-design` отвечает за визуальное качество и характер решения.
- Не подменяй навык `frontend-design` общими правилами контракта сценариев.
- Файлы прототипов считай утвержденным набором сценариев: они не обязаны быть сделаны по общей болванке, но обязаны быть кликабельны по основным пользовательским маршрутам проверки.
- Для `--screen-data` используй только логический field id в формате `<screen-id>::<displayed|input>::<name>`; не добавляй туда описания и дополнительные `::` сегменты.
- Любое подтвержденное изменение в экране, потоке, навигации, платформенном поведении, данных на экране или покрытии функций обязано сопровождаться проверкой и актуализацией связанных дизайн-артефактов и структурированной памяти.
- Не показывай пользователю `P1/P2/P3` как визуальные бейджи в прототипе; приоритеты нужны для внутреннего покрытия, а не для проверки сценариев.

### `mvp.tech`

- Работай начиная с памяти: источник истины — `.madspec/<branch>/memory/stages/mvp.tech.json`, а `tech-stack.md` является производным артефактом и не редактируется вручную.

### `mvp.architecture`

- В обычных ходах используй `madspec memory retrieve --stage mvp.architecture --toon-output` и опирайся на `architecture_status`.
- `--full-artifact` запрашивай только перед итоговой валидацией и `checkpoint`.
- Источник истины — `.madspec/<branch>/memory/stages/mvp.architecture.json`, а `architecture.md`, `data-model.md` и `contracts/openapi.yaml` являются производными артефактами и не редактируются вручную.
- У `--endpoint-field` секция `response` допустима как shorthand для `response:200`; если нужен конкретный статус ответа, используй `response:<status>`.
- Если архитектурная валидация выглядит ложной, не редактируй `.madspec/<branch>/memory/stages/*.json` вручную: сначала проверь `screen.data` и `endpoint-field`, затем исправляй состояние только через `madspec memory capture` или `checkpoint`.

### `mvp.plan`

- В обычных ходах используй `madspec memory retrieve --stage mvp.plan --toon-output` и опирайся на `plan_status`.
- `--full-artifact` запрашивай только перед итоговой валидацией и `checkpoint`.
- Источник истины — `.madspec/<branch>/memory/stages/mvp.plan.json`, а `implementation-plan.md` и `planning-context-cache.md` являются производными артефактами и не редактируются вручную.
- Вместе с `plan_status` всегда проверяй `policy_context`: план шага, `stepKind`, `tddPolicy` и зависимости не должны расходиться с активными обязательными правилами.
- Выбирай максимально крупный безопасный шаг для текущей итерации; легкую задачу планируй одним шагом, а не серией микро-шагов.
- Не выноси отдельно подготовку, тесты, документацию и валидацию, если они относятся к одному и тому же изменению и не создают самостоятельной зависимости.
- Дроби план только при реальных зависимостях, разных точках проверки, заметно разных рисках или явной просьбе пользователя о большей детализации.
- При отклонении `register-step` сначала смотри `gate_summary` или запускай `madspec gate explain`, а не редактируй `progress.json` вручную.
- Если существует `deployment.md`, учитывай ограничения развертывания при составлении шагов, тестов и проверки результата.

### `deploy`

- Источник истины — `.madspec/<branch>/memory/stages/deploy.json`.
- `.madspec/<branch>/deployment.md` является производным представлением и не редактируется вручную.
- В обычных ходах используй `madspec memory retrieve --stage deploy --toon-output` и опирайся на `deploy_status`.
- Полное состояние этапа запрашивай только перед итоговой валидацией и `checkpoint`.
- Сначала читай технические и инфраструктурные артефакты репозитория, а уже потом задавай вопросы пользователю.
- Этап можно запускать как перед `mvp.plan`, так и отдельно позже, после реализации, review или security, если способ выкладки уточнился.

### `mvp.implement`

- Перед каждой сессией запускай `madspec memory retrieve --stage mvp.implement --toon-output`.
- Если не хватает контекста ветки, используй `--query` или `madspec memory search`.
- Стартуй шаг через `madspec memory start-step`.
- Фиксируй `red/green/refactor` через `madspec memory checkpoint-step`.
- Завершай шаг только через `madspec memory complete-step`.
- После завершения TDD-цикла проверяй итог повторным `retrieve`, а `implementation-context.md` используй только как производную сводку.
- Считай `.madspec/system/memory/memory.sqlite` каноническим рабочим хранилищем, а `.madspec/<branch>/memory/progress.json` и `.madspec/<branch>/memory/working/active-session.json` — проекциями состояния ветки и слоем совместимости; `implementation-context.md` и `project-context.md` — это производные представления, которые не редактируются вручную как источник истины.
- Для `mvp.implement` и `feature.implement` вместе с рабочим состоянием всегда проверяй `policy_context`; если завершение блокируется, сначала запусти `madspec policy validate`, а не редактируй память вручную.
- При отклонении `start-step`, `checkpoint-step` или `complete-step` сначала смотри `gate_summary` из `madspec memory explain` или запускай `madspec gate explain`, а не правь runtime state вручную.

## Feature-поток

- Для процесса работы с фичей не пропускай `feature.init` перед `feature.plan`.

### `feature.init`

- Источник истины — `.madspec/<branch>/memory/stages/feature.init.json`.
- `project-analysis.md`, `feature-context.md`, `tech-stack.md` и `architecture.md` являются производными представлениями.
- `feature.init` не должен заранее материализовать `implementation-plan.md`, `planning-context-cache.md`, `review.md`, `security-audit.md` и несвязанные производные артефакты MVP.

### `feature.plan`

- Источник истины — `.madspec/<branch>/memory/stages/feature.plan.json`.
- `implementation-plan.md`, `planning-context-cache.md` и `planning-context.md` являются производными представлениями.
- Эти planning-артефакты появляются лениво при первом реальном входе в `feature.plan` или через команды полной пересборки памяти.
- Выбирай максимально крупный безопасный шаг для текущей feature-итерации; небольшое изменение планируй одним шагом, если его можно реализовать и проверить как единое целое.
- Не создавай искусственные шаги только ради разделения кода, тестов, документации или мелких сопутствующих правок, если это один результат.
- Делить feature на несколько шагов нужно только при реальных зависимостях, разных точках проверки, заметно разных рисках или явной просьбе пользователя.
- При отклонении `register-step` сначала смотри `gate_summary` или запускай `madspec gate explain`, а не редактируй `progress.json` вручную.
- Если существует `deployment.md`, учитывай его ограничения при планировании и проверке feature-шага.

### `feature.implement`

- Работай так же, как для `mvp.implement`: перед каждой сессией запускай `madspec memory retrieve --stage feature.implement --toon-output`, затем `start-step -> checkpoint-step -> complete-step`.

## Review и Security

### `review`

- Команда кросс-сценарная: она может запускаться после `mvp.implement` или `feature.implement`.
- Нужно читать кодовую базу, `memory/progress.json`, `active-session.json`, `implementation-plan.md`, доступные контексты шагов и артефакты ветки.
- Отсутствие части артефактов фиксируй как ограничение, а не как автоматический отказ.
- Для `review` и `security` считывай `change_context` из `madspec memory retrieve --stage review|security --toon-output`; если пакет изменений активен, сверяй вывод с его `title`, `summary` и списком затронутых шагов.
- Перед выводами отдельно проверяй `madspec review status --toon-output`, если этот вывод читает агент: блокирующие и ожидающие проверки, а также активные исключения должны быть отражены в findings, limitations или принятых компромиссах.
- После `madspec memory retrieve --stage review --toon-output` отдельно запускай `madspec policy validate --stage review --toon-output` и сопоставляй обязательные нарушения с замечаниями, подтверждения с фактами, а рекомендательные результаты — со списком улучшений или открытых вопросов.
- Сохраняй замечания через `madspec memory capture --stage review` с сопоставлением: наблюдения и проблемы -> `--fact`, направления улучшения и компромиссы -> `--decision`, открытые вопросы -> `--question`, конкретные последующие действия -> `--pending-action`.

### `security`

- Работай начиная с памяти и контекста ветки: читай кодовую базу, состояние прогресса и выполнения, `tech-stack.md`, `architecture.md`, `deployment.md` и предыдущие записи `security` по мере наличия.
- Перед выводами отдельно проверяй `madspec security status --toon-output`, если этот вывод читает агент: блокирующие и ожидающие проверки, а также активные исключения должны быть отражены в findings, limitations или принятых компромиссах.
- Контекстом приватности и соответствия требованиям считай только 152-ФЗ; не обещай универсальную проверку сразу для нескольких юрисдикций и не используй `--jurisdiction`.
- Классифицируй риски по уровням серьезности `critical/high/medium/low`, а не через обязательную числовую оценку.
- Если есть `deployment.md`, учитывай секреты, CI/CD, разделение окружений, наблюдаемость и риски выката; если файла нет, фиксируй это как ограничение анализа.

## Изменения в UI, архитектуре и деплое

- Если менялись HTML/CSS-прототипы, проверь, не устарели ли `ui-design.md`, навигация, пользовательские маршруты проверки, покрытие функций и ссылки на файлы прототипов.
- Для UI-реализации сверяй не только `ui-design.md`, но и конкретные screen-прототипы, flow steps и точку входа приложения на `ui-prototype/index.html`; если реализация хочет отойти от сценария, сначала вернись к `mvp.design` или явно зафиксируй согласование такого отклонения.
- Если менялась архитектура, модель данных или контракты, обновляй каноническое состояние архитектуры через `madspec memory capture`, затем пересобирай производные артефакты и проверяй память.
- Если деплой влияет на архитектуру, интеграции, секреты, миграции или наблюдаемость, учитывай `deployment.md` или инициируй `/madspec.deploy`.
