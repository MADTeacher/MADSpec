# MADSpec

MADSpec - фреймворк для разработки программного обеспечения с помощью LLM-агентов. Он дает команде понятную структуру проекта, процесс работы с учетом веток и слой структурированной памяти, чтобы контекст и принятые решения не терялись между сессиями.

## Кому Подходит

- Командам, которые хотят работать с AI-агентами более предсказуемо
- Проектам, где важно сохранять прозрачность архитектурных решений и прогресса реализации
- Пользователям Cursor, GitHub Copilot, opencode, Roo Code, Kilo Code, SourceCraft и Qwen Code, которым нужен единый процесс работы

## Что Дает MADSpec

- MVP-процесс для разработки продукта с нуля: от концепции до реализации
- Feature-процесс для добавления функциональности в существующий код
- Отдельные артефакты по веткам в `.madspec/<branch>/` вместо одного общего состояния проекта
- Проектное хранилище памяти в `.madspec/system/memory/`, артефакты памяти ветки в `.madspec/<branch>/memory/` и автоматически собираемые Markdown-файлы поверх них
- Локальное состояние выполнения для каждой сессии хранится в `SQLite`
- Полный протокол параллельной работы нескольких агентов включен по умолчанию
- Слой объяснения и диагностики для структурированной памяти: `doctor`, `explain`, `timeline`, `why-next-step`, `conflicts`, `inspect-record`
- Контролируемое сравнение и слияние памяти между ветками с циклом `compare/propose/preview/apply` и продвижением подтвержденных знаний на уровень проекта
- Единый слой правил проекта в `.madspec/system/policy/` с циклом `предложение -> применение` и автоматически собираемым `policy.md`
- Слой управления изменениями в `.madspec/<branch>/change/` с фиксированной базовой точкой сравнения, предложениями, ратифицированным пакетом изменений и переносимым пакетом экспорта
- Слой контрольных проверок в `.madspec/<branch>/gates/` с единым статусом переходов, предложениями на исключения и журналом аудита
- Слой субагентных профилей в `.madspec/system/agents/` с каноническим состоянием ролей, рекомендациями, историей изменений и контекстом, подготовленным для каждой роли
- Процессы `review` и `security` для проверки качества после реализации
- Подготовленную структуру команд и файлов для поддерживаемых сред с AI-агентами

## Установка

### Требования

- Python 3.11+
- [uv](https://docs.astral.sh/uv/)
- Git
- Один из поддерживаемых AI-агентов

### Постоянная Установка

```bash
uv tool install madspec-cli --from git+https://github.com/MADTeacher/MADSpec.git
```

Базовое использование:

```bash
madspec init <PROJECT_NAME> --ai cursor-agent
madspec init .
madspec check
```

Если использовать `madspec init .` без `--ai`, MADSpec инициализирует проект в текущей директории и предложит вручную выбрать AI-среду во время запуска.

Обновление:

```bash
uv tool install madspec-cli --force --from git+https://github.com/MADTeacher/MADSpec.git
```

### Одноразовый Запуск

```bash
uvx --from git+https://github.com/MADTeacher/MADSpec.git madspec init <PROJECT_NAME>
```

## Как Работать С MADSpec

Все сгенерированные команды со слешем `madspec.*` должны начинаться с чтения и применения навыка `madspec-cli-operator`. Для `madspec.mvp.design` дополнительно обязателен навык `frontend-design`.

### MVP-Процесс

Используйте команды `madspec.mvp.*`, когда создаете продукт с нуля:

Базовый порядок стадий:

1. Если хотите сразу создать новый проект вместе с MADSpec, используйте `madspec init <PROJECT_NAME> --ai <agent>`.
2. Если директория проекта уже существует, используйте `madspec init .`; при необходимости AI-среду можно передать через `--ai <agent>` или выбрать вручную во время запуска.
3. `/madspec.mvp.concept` - зафиксировать идею проекта, целевую аудиторию, сценарии и ключевые функции.
4. `/madspec.mvp.design` - описать пользовательский опыт, экраны и прототипы интерфейса с реальной точкой входа приложения; на этой стадии агент обязан использовать оба навыка: `madspec-cli-operator` как базовый навык процесса и CLI, а `frontend-design` - для визуального проектирования интерфейса.
5. `/madspec.mvp.tech` - выбрать стек технологий и зафиксировать технические решения.
6. `/madspec.mvp.architecture` - формализовать структуру проекта, модель данных и контракты.
7. `/madspec.deploy` - при необходимости заранее зафиксировать окружения, выкладку, секреты, миграции, наблюдаемость, релиз и откат.

После этого можно работать по одному из двух сценариев.

#### Вариант 1: сначала полностью допланировать, потом реализовывать

1. Повторять `/madspec.mvp.plan`, пока план не будет готов полностью.
2. Запустить `/madspec.mvp.implement` для текущего запланированного шага.
3. После каждого прохода `implement` разработчик вручную запускает софт и проверяет результат.
4. Если текущий шаг реализован некорректно, разработчик возвращается к агенту и просит исправить именно этот шаг.
5. Если текущий шаг реализован корректно, разработчик смотрит, завершены ли все уже запланированные шаги.
6. Если не завершены, снова запускается `/madspec.mvp.implement` для следующего шага.
7. Когда все запланированные шаги завершены, можно переходить к `/madspec.review` и `/madspec.security`.

#### Вариант 2: идти итерациями plan -> implement

1. Запланировать следующий шаг через `/madspec.mvp.plan`.
2. Сразу реализовать этот шаг через `/madspec.mvp.implement`.
3. После `implement` разработчик вручную запускает софт и проверяет результат.
4. Если текущий шаг реализован некорректно, разработчик возвращается к агенту и добивается исправления текущего шага.
5. Если текущий шаг реализован корректно, разработчик решает, завершена ли разработка.
6. Если разработка не завершена, процесс снова идет на `/madspec.mvp.plan` для следующего шага.
7. Если разработка завершена, можно переходить к `/madspec.review` и `/madspec.security`.

```bash
# если хотите сразу создать новый проект
madspec init <PROJECT_NAME> --ai <agent>

# если проект уже существует в текущей директории
madspec init .
/madspec.mvp.concept "Идея проекта"
/madspec.mvp.design
/madspec.mvp.tech
/madspec.mvp.architecture
/madspec.deploy
/madspec.mvp.plan
/madspec.mvp.implement
```

Подробности по каждой стадии есть в [документации MVP-процесса](docs/mvp/README.md).

### Feature-Процесс

Используйте команды `madspec.feature.*`, когда добавляете функциональность в существующий проект:

Базовый порядок:

1. Если проект еще не был инициализирован через MADSpec, сначала выполнить `madspec init . --ai <agent>` в корне существующего проекта.
2. Работать в существующем проекте и нужной ветке.
3. Запустить `/madspec.feature.init`, чтобы зафиксировать контекст новой функции.

После `feature.init` тоже возможны два сценария работы.

Для небольшой feature агент должен предпочитать один полный шаг планирования, если изменение можно реализовать и проверить как единое целое. Не нужно разносить код, тесты, документацию и валидацию по отдельным шагам без реальной зависимости между ними.
Идентификаторы feature и приоритеты служат для учета покрытия и выбора очередности, а не как требование дробить план на множество запусков команды.

#### Вариант 1: сначала полностью допланировать feature, потом реализовывать

1. Повторять `/madspec.feature.plan`, пока feature-план не будет готов полностью.
2. Запустить `/madspec.feature.implement` для текущего запланированного шага.
3. После каждого прохода `implement` разработчик вручную запускает софт и проверяет результат.
4. Если текущий шаг реализован некорректно, разработчик возвращается к агенту и просит исправить именно этот шаг.
5. Если текущий шаг реализован корректно, разработчик смотрит, завершены ли все уже запланированные шаги.
6. Если не завершены, снова запускается `/madspec.feature.implement` для следующего шага.
7. Когда все запланированные шаги завершены, можно переходить к `/madspec.review` и `/madspec.security`.

#### Вариант 2: идти итерациями plan -> implement

1. Запланировать следующий шаг через `/madspec.feature.plan`.
2. Сразу реализовать этот шаг через `/madspec.feature.implement`.
3. После `implement` разработчик вручную запускает софт и проверяет результат.
4. Если текущий шаг реализован некорректно, разработчик возвращается к агенту и добивается исправления текущего шага.
5. Если текущий шаг реализован корректно, разработчик решает, завершена ли работа над feature.
6. Если feature еще не завершена, процесс снова идет на `/madspec.feature.plan` для следующего шага.
7. Если feature завершена, можно переходить к `/madspec.review` и `/madspec.security`.


```bash
# если проект еще не инициализирован через MADSpec
madspec init . --ai <agent>

/madspec.feature.init "Описание новой функции"
/madspec.feature.plan
/madspec.feature.implement
```

Подробности по этому сценарию есть в [документации Feature-процесса](docs/feature/README.md).

### Роль Разработчика

MADSpec не предполагает слепого выполнения всего процесса агентом без участия человека.

- После каждого прохода `implement` разработчик должен запустить софт и посмотреть, работает ли он так, как ожидалось
- Если результат не устраивает, разработчик возвращается к агенту с корректировками и направляет его дальше
- Если результат устраивает, разработчик либо переходит к следующему шагу, либо завершает работу через `review` и `security`
- Чем меньше доверия к агенту в конкретной задаче, тем важнее ручная проверка и коррекция после реализации

### Общие Команды

Эти команды можно запускать после заметных изменений в любом режиме:

- [`/madspec.memory`](docs/other/madspec.memory.md) — помогает понять текущее состояние структурированной памяти: почему выбран следующий шаг, какие записи влияют на контекст, где есть конфликты и что требует уточнения
- [`/madspec.merge`](docs/other/madspec.merge.md) — помогает сравнить память текущей ветки с другой веткой, подготовить предложение на слияние и продвинуть подтвержденные знания на уровень проекта
- [`/madspec.policy`](docs/other/madspec.policy.md) — используется для разговорной работы с правилами проекта: посмотреть действующие правила, подготовить изменение, увидеть различия и применить его через CLI после подтверждения
- [`/madspec.change`](docs/other/madspec.change.md) — помогает собрать и ратифицировать пакет изменений ветки относительно базовой точки сравнения перед проверкой качества, передачей работы или переносом изменений
- [`/madspec.gate`](docs/other/madspec.gate.md) — показывает состояние контрольных проверок, блокировки переходов, предупреждения и процесс оформления исключений
- [`/madspec.agents`](docs/cli/agents.md) — помогает управлять профилями субагентов, включенными ролями, проектными описаниями ролей и контекстом, подготовленным для конкретного субагента
- [`/madspec.review`](docs/other/madspec.review.md) — запускает проверку качества реализации с учетом контекста текущей ветки, сверяет код и артефакты с замыслом ветки и формирует список улучшений
- [`/madspec.security`](docs/other/madspec.security.md) — запускает практический аудит безопасности и приватности по набору изменений, зависимостям, обработке данных и архитектурным рискам
- [`/madspec.deploy`](docs/other/madspec.deploy.md) — фиксирует план развертывания для текущей ветки; команду можно запускать как перед `mvp.plan`, так и отдельно позже, когда способ выкладки стал понятнее

Подробная карта всех команд есть в [общей документации](docs/README.md), а терминальные команды `madspec ...` собраны в [CLI-документации](docs/cli/README.md).

## Структурированная Память

MADSpec вводит модель памяти не ради отдельного хранилища как такового, а ради устойчивого контекста работы. В длинной разработке с ветками, несколькими сессиями и параллельными агентами недостаточно просто держать набор Markdown-файлов: их удобно читать, но они плохо подходят на роль главного источника истины, если нужно фиксировать изменения последовательно, объяснять, почему выбран следующий шаг, и восстанавливать состояние после конфликтов или пересборки.

Поэтому в MADSpec модель памяти разделена на два слоя. Первый слой отвечает на вопрос "что считается действительным состоянием проекта и процесса". Второй слой отвечает на вопрос "как быстро найти релевантный контекст по смыслу, если пользователь или агент не знает точный файл, стадию или формулировку".

### Канонический Слой

Канонический слой хранит подтвержденное состояние процесса: записи, снимки стадий, состояние конкретной сессии, ревизии выполнения и другие рабочие данные, от которых зависит поведение команд. Главный источник истины для этого слоя находится в `.madspec/system/memory/memory.sqlite`.

Практический смысл канонического слоя такой:

- он фиксирует согласованное состояние ветки и проекта;
- он позволяет безопасно обновлять процесс и восстанавливать его после сбоев пересборки;
- он отделяет реальные данные от удобных для чтения представлений.

Файлы в `.madspec/<branch>/memory/`, а также производные `json`, `jsonl` и Markdown-представления вроде `concept.md`, `architecture.md` или `implementation-plan.md` остаются проекциями. Они собираются из канонического состояния и удобны для чтения, но не подменяют его.

### Семантический Слой

Семантический слой нужен не для хранения истины, а для поиска релевантного контекста по смыслу. Он работает поверх канонических записей и использует векторный индекс в `.madspec/system/memory/lancedb/`, чтобы команды `madspec memory search` и `madspec memory retrieve` могли находить полезные записи даже тогда, когда запрос не совпадает с текстом буквально.

Важно не смешивать разные сущности:

- модель памяти MADSpec — это вся архитектура хранения и извлечения контекста;
- канонический слой — это источник истины;
- локальная embedding-модель — это только инструмент семантического поиска внутри этого слоя чтения.

Семантический слой улучшает поиск, но не становится самостоятельным хранилищем знаний. Если в каноническом слое нет подтвержденной записи, семантический индекс не должен восприниматься как более надежная версия истины.

### Как Слои Работают Вместе

Типовой поток работы выглядит так:

1. Команда записывает или обновляет каноническое состояние.
2. Из него пересобираются веточные проекции и производные представления.
3. Семантический индекс использует эти канонические данные как материал для поиска по смыслу.
4. `retrieve` и `search` собирают ответ из точного, полнотекстового и семантического сигналов.
5. `doctor`, `status` и `db-status` помогают понять, где возникла проблема: в каноническом состоянии, в проекциях, в модели или в активном индексе.

Из-за этого подготовка локальной embedding-модели и переиндексация решают разные задачи. `madspec memory bootstrap-model` подготавливает локальный кэш модели, а `madspec memory reindex` пересобирает активное пространство индекса для текущей конфигурации. Одно не заменяет другое.

### Варианты Семантического Поиска

Выбор прикладного семантического режима хранится в `.madspec/config.json` через блок `memory.embeddings`.

| Вариант | Что хранится в `memory.embeddings` | Нужна загрузка модели | Когда подходит | Что сделать после выбора |
| --- | --- | --- | --- | --- |
| `hash` | `provider=hash`, `model=null`, `downloadPolicy=none` | Нет | Нужен совместимый режим без локальной модели и без подготовки кэша | Можно работать сразу после `madspec init`; отдельная подготовка модели не нужна |
| `local-hf-onnx` | `provider=local-hf-onnx`, `model=<ключ модели>`, `downloadPolicy=<policy>` | Да, если кэш модели еще не подготовлен | Нужен локальный поиск по смыслу с реальными embeddings | Подготовить кэш модели автоматически или вручную, затем поддерживать активное пространство индекса через `madspec memory reindex` |

Для `local-hf-onnx` доступны две модели:

- `multilingual-e5-small` — рекомендуемый вариант, около 470 MB
- `bge-m3` — более тяжелый вариант, около 2300 MB

Политика загрузки определяет, когда подготавливается локальный кэш модели:

- `on-init` скачивает модель сразу во время `madspec init`
- `on-first-use` откладывает загрузку до первого сценария, которому действительно нужен поиск по смыслу
- `none` не запускает загрузку автоматически и оставляет ручную подготовку через `madspec memory bootstrap-model`

Если меняется `memory.embeddings.provider`, `memory.embeddings.model` или `memory.embeddings.revision`, одного изменения конфига недостаточно: после подготовки кэша нужно выполнить `madspec memory reindex`, чтобы пересобрать активное пространство индекса для новой конфигурации.

Минимальные примеры:

```bash
# режим по умолчанию: hash без загрузки модели
madspec init my-project --ai cursor-agent

# локальная модель с отложенной загрузкой
madspec init my-project --ai cursor-agent --memory-provider local-hf-onnx --memory-model multilingual-e5-small --memory-download-policy on-first-use
```

Подробная настройка режимов памяти, моделей и политик загрузки описана в [docs/cli/init.md](docs/cli/init.md).

## Дополнительно

### Навыки Агента

Во время инициализации MADSpec также копирует навыки агента в целевую среду из каталога `skills/`, включая:

- [`madspec-cli-operator`](skills/madspec-cli-operator/SKILL.md) — базовый операторский навык, который должны читать все команды `madspec.*`
- [`madspec-memory-explain`](skills/madspec-memory-explain/SKILL.md) — навык объяснения и диагностики для `madspec.memory` и навигации по структурированной памяти
- [`madspec-merge-assistant`](skills/madspec-merge-assistant/SKILL.md) — навык для межветочного сравнения памяти, подготовки предложений на слияние и продвижения подтвержденных знаний на уровень проекта
- [`madspec-policy-engine`](skills/madspec-policy-engine/SKILL.md) — навык для жизненного цикла проектных правил через `madspec policy ...`: просмотр, предложение, применение, вывод из действия и проверка влияния правил на процесс
- [`madspec-change-engine`](skills/madspec-change-engine/SKILL.md) — навык для жизненного цикла `madspec change ...` и разговорной команды `/madspec.change`
- [`madspec-gate-orchestrator`](skills/madspec-gate-orchestrator/SKILL.md) — навык для `madspec gate ...`, блокировок, исключений и статуса ратификации
- [`madspec-subagent-role-advisor`](skills/madspec-subagent-role-advisor/SKILL.md) — навык для `madspec agents ...`, профилей субагентов и контекста, подготовленного под конкретную роль
- [`frontend-design`](skills/frontend-design/SKILL.md) — навык для проектирования выразительных интерфейсов и фронтенд-артефактов с сильным визуальным направлением, рабочим кодом и отказом от шаблонной «AI-эстетики»
- [`madspec-generate-agents-md`](skills/madspec-generate-agents-md/SKILL.md) — навык для создания и обновления `AGENTS.md` и родственных файлов с инструкциями для агентов как краткого операционного контракта

### Субагенты

MADSpec хранит каноническое состояние субагентных ролей в `.madspec/system/agents/` и экспортирует контекст, подготовленный для конкретной роли, через `madspec agents subagents context`. Эта команда теперь также принимает `--session-key`, чтобы читать локальный контекст выполнения нужного агента без вмешательства в чужие сеансы.

Основные файлы:

- `.madspec/system/agents/state.json` — активная среда, профиль и `enabledSubagentIds`
- `.madspec/system/agents/catalog.json` — проектные роли и проектные переопределения встроенных ролей
- `.madspec/system/agents/bodies/` — Markdown-описания проектных ролей и переопределений

Через `madspec agents subagents create/update/remove` можно добавлять собственные проектные роли, не меняя напрямую встроенный каталог фреймворка.

Во встроенный начальный набор входят роли:

- `architecture` — отвечает за архитектурные решения, границы системы, интерфейсы и ключевые компромиссы
- `developer` — реализует согласованные изменения в коде и тестах, а также фиксирует результаты проверки
- `contracts-data` — отвечает за API-контракты, схемы данных, сущности и согласованность интеграционных моделей
- `testing` — отвечает за стратегию проверки, тестовое покрытие, сценарии валидации и подтверждение корректности реализации
- `security` — анализирует риски безопасности и приватности, поверхность атаки, зависимости и защитные меры
- `research` — исследует кодовую базу, собирает контекст, сравнивает варианты и подготавливает доказательную базу для следующих шагов
- `docs` — поддерживает пользовательскую и техническую документацию в соответствии с реальным процессом, кодом и артефактами проекта

- Для Cursor, GitHub Copilot, OpenCode и Qwen Code MADSpec генерирует встроенные файлы агентов и субагентов в директориях выбранной среды.
- Для Kilo Code, Roo Code и SourceCraft v1 MADSpec использует запасные адаптеры на базе `rules`, `commands` и `skills` без собственного механизма исполнения.
- Сам MADSpec не управляет расписанием субагентов: параллельность и последовательность остаются возможностями выбранной агентной среды.
