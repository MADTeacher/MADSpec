## Правила диалога (обязательно)

- **Задавай вопросы строго по одному**: в каждом твоем сообщении должен быть **ровно 1 вопрос**, который требует ответа.
- **Не выдавай список вопросов заранее**.
- Если нужен выбор, задай **один вопрос** и предложи **не больше 3-5 вариантов** или попроси свободный ответ.
- **Дожидайся ответа** и только затем задавай следующий вопрос.
- Если задача маленькая и контекст уже восстановим из артефактов, не превращай работу в длинное интервью.

## Structured Memory First (обязательно)

- `progress.json`, `active-session.json`, decision log и episodes — канонический workflow state.
- Каноническое состояние этапа plan хранится в `.madspec/<BRANCH>/memory/stages/mvp.plan.json`.
- Для архитектурного контекста сначала используй `madspec memory retrieve --stage mvp.architecture --toon-output`, если этот контекст читает агент, а `architecture.md`, `data-model.md` и `contracts/openapi.yaml` считай generated views поверх canonical architecture-state.
- `implementation-plan.md`, `planning-context-cache.md`, `planning-context.md` и `project-context.md` являются generated views.
- В обычных ходах диалога сначала используй `madspec memory retrieve --stage mvp.plan --toon-output`, если этот контекст читает агент, и опирайся на `plan_status`.
- Из ответа `madspec memory retrieve` **обязательно** прочитай `policy_context.required`, `policy_context.advisory` и `policy_context.pending_proposals_count`; planning decisions и новые step metadata не должны противоречить active policies текущей стадии.
- Полный `artifact_state.plan` запрашивай только перед финальной проверкой и `madspec memory checkpoint --stage mvp.plan`, используя `--full-artifact`.
- Для planning-level state используй `madspec memory capture --stage mvp.plan --plan-overview ... --planning-principle ... --next-action ...`.
- После обновления structured memory запускай `madspec memory consolidate` и `madspec memory validate`, когда это действительно нужно для проверки результата прохода; не делай это механически после каждого мелкого действия.
- Перед фиксацией нового шага **обязательно** проверь кандидата через `madspec memory next-step --stage mvp.plan --candidate-step <step-id> --depends-on <dependency>...`.
- Перед `madspec memory register-step` сначала создай или обнови step source artifacts в `.madspec/<BRANCH>/steps/<step-id>/`.
- Для записи нового planned step в canonical state используй `madspec memory register-step --stage mvp.plan --step-id <step-id> --step-kind <code|non-code> --title <title> --summary <summary> --covers <function> --related-artifact <path> --size <small|medium|large> --complexity <low|medium|high> ...`, а не ручное редактирование `progress.json`.
- Ратифицируй состояние через `madspec memory checkpoint --stage mvp.plan ...` после завершенного прохода планирования; не делай отдельный `checkpoint` после каждого небольшого изменения, если один итоговый `checkpoint` покрывает весь проход.
- **ОБЯЗАТЕЛЬНО**: для вызовов `madspec memory capture`, `madspec memory checkpoint` и `madspec memory register-step` используй `--from-file`: записывай аргументы во временный JSON-файл в `.madspec/.tmp/` и передавай путь через `--from-file <path>` (например, `madspec memory register-step --from-file .madspec/.tmp/register-args.json --json-output`). При ошибке исправляй тот же файл и повторяй вызов; после успешной команды CLI удалит файл автоматически. Ключи JSON соответствуют именам полей команды, плюс `stage`, `branch`, `json_output` на верхнем уровне.

- Если `currentImplementStep` содержит имя шага, оставь его без изменений.

## Описание

На этом этапе **MADSpec (MADSpec Framework)** **MVP (Minimum Viable Product)** проект разбивается на конкретные шаги реализации с использованием memory-first workflow.

**Режим MVP**: Эта команда предназначена для разработки нового проекта с нуля. Все артефакты сохраняются в `.madspec/<BRANCH>/`, где `<BRANCH>` — имя текущей ветки разработки.

Каждый шаг должен быть:
- независимо тестируемым;
- имеющим четкие критерии завершения;
- содержащим описание того, что нужно сделать;
- включающим тесты для валидации;
- покрывающим хотя бы одну функцию из концепции проекта или явный технический результат, необходимый для поставки;
- явно классифицированным как `code` или `non-code`.

## Правила гранулярности шага (обязательно)

- Стремись к **минимально достаточному плану**.
- Для легкой задачи или маленькой MVP-итерации по умолчанию создавай **один полный шаг**, даже если в нем нужно сделать код, тесты, конфигурацию и документацию как части одного результата.
- Не дроби план на отдельные шаги вида "подготовка", "написание тестов", "обновление документации", "валидация", если это части одной и той же поставки.
- Делить работу на несколько шагов можно только при реальных зависимостях, отдельных точках пользовательской проверки, заметно разных рисках или явной просьбе пользователя получить более подробный план.
- Если нет убедительной причины дробить сильнее, выбирай меньшее число шагов.
- `P1/P2/P3` используются для покрытия и очередности функций, а не как правило "по одному шагу на каждую функцию".
- Не создавай отдельный "setup step" только потому, что это первый запуск команды, если функциональный шаг можно описать и проверить сразу.

## TDD policy (обязательно)

- Для `code` шага TDD обязателен: план должен описывать `red -> green -> refactor`.
- Для `code` шага в `tests.md` должны быть явно указаны:
  - failing test или assertion, который должен сначала падать;
  - минимальная реализация для перехода в green;
  - relevant suite или regression suite после green;
  - refactor intent или явное `no refactor needed`.
- Для `non-code` шага должен быть заполнен TDD waiver с причиной и шаг должен регистрироваться через `--step-kind non-code` и `--tdd-policy waived|not-applicable`.
- По умолчанию новый `code` шаг регистрируется с `tddPolicy=required` и `tddPhase=not_started`.

  - `.madspec/<BRANCH>/concept.md`
  - `.madspec/<BRANCH>/ui-design.md`
  - `.madspec/<BRANCH>/tech-stack.md`
  - `.madspec/<BRANCH>/architecture.md`

- Рекомендуется: `.madspec/<BRANCH>/deployment.md`
  - Если `.madspec/<BRANCH>/deployment.md` существует, ты **ОБЯЗАН** прочитать его и учитывать зафиксированные ограничения развертывания при планировании шагов.
  - Если файла нет, продолжай планирование, но при появлении существенных вопросов про окружения, CI/CD, секреты, миграции, наблюдаемость или откат предложи выполнить `/madspec.deploy`.
- Если файлы отсутствуют, предложи выполнить предыдущие этапы MVP: `/madspec.mvp.concept`, `/madspec.mvp.design`, `/madspec.mvp.tech`, `/madspec.mvp.architecture`.
- При планировании шага, который реализует функцию:
  - проверь наличие связанных артефактов: UI-дизайн, контракты API, модели данных;
  - если такие файлы существуют, они **ОБЯЗАТЕЛЬНО** должны быть связаны в описании шага;
  - для UI-шага явно свяжи step с конкретными screen prototypes, flow и входным экраном, а не только с общей директорией `ui-prototype/`.

## Цель этапа

Создать **минимально достаточный план реализации**, который:
- разбивает проект на логические шаги только там, где это действительно нужно;
- определяет зависимости между шагами;
- включает тесты для каждого шага;
- позволяет отслеживать прогресс покрытия всех функций `P1`, `P2`, `P3`;
- оптимизирует использование контекстного окна через кэширование контекста;
- визуализирует прогресс планирования после каждого завершенного прохода.

**ВАЖНО**: один запуск команды **может** ограничиться одним новым шагом, и для простого проекта это обычно правильный выбор. Но это не обязательное правило процесса само по себе: если без этого нельзя зафиксировать минимально достаточный план, допустимо зарегистрировать несколько тесно связанных шагов в одном проходе.

0. **Определение текущей ветки**:
   - Перед началом работы определи текущую ветку, выполнив `madspec git current-branch` из корня проекта.
   - Команда возвращает имя ветки через stdout.
   - Используй результат выполнения команды для формирования путей к артефактам.
   - Все пути к артефактам должны быть в формате `.madspec/<BRANCH>/...`, где `<BRANCH>` — имя ветки, полученное из команды.
   - Если ни команда, ни файл недоступны, используй значение по умолчанию `main`.

1. **Проверка состояния планирования**:
   - Проверь существование `.madspec/<BRANCH>/memory/progress.json` и `.madspec/<BRANCH>/memory/stages/mvp.plan.json`.
   - Если файлов нет:
     - выполни `madspec memory init`;
     - установи режим работы `initial`.
   - Если файл существует:
     - прочитай `plannedSteps` и `planningMetadata`;
     - определи режим работы:
       - `initial`, если `plannedSteps` пуст или отсутствует;
       - `incremental`, если `plannedSteps` не пуст.

2. **Режим Initial (первый запуск)**:

   - **Проверка наличия артефактов**:
     - Если какой-либо обязательный файл отсутствует или поврежден:
       - сообщи об ошибке;
       - укажи, какой файл отсутствует;
       - предложи выполнить предыдущие этапы для создания недостающих артефактов;
       - **НЕ ПРОДОЛЖАЙ** планирование до устранения проблемы.

   - Загрузи все предыдущие артефакты:
     - `.madspec/<BRANCH>/concept.md` для понимания функций и приоритетов;
     - `madspec memory retrieve --stage mvp.architecture --toon-output` как основной summary архитектуры, если этот вывод читает агент; из ответа также прочитай `policy_context`;
     - `.madspec/<BRANCH>/architecture.md`, `.madspec/<BRANCH>/ui-design.md`, `.madspec/<BRANCH>/tech-stack.md`, `.madspec/<BRANCH>/data-model.md` как generated views, если нужны детали;
     - если существует `.madspec/<BRANCH>/deployment.md`, загрузи его и учитывай ограничения развертывания при планировании шагов.

   - Проанализируй архитектуру и определи **минимально достаточный** стартовый набор шагов.

   - **Проверь наличие связанных артефактов**:
     - Для функции, которую планируется реализовать в шаге, проверь наличие:
       - **UI-дизайна**:
         - файл с описанием дизайна UI;
         - HTML storyboard-прототипы;
         - конкретный flow, входной экран и screen-файлы, которые шаг не должен сломать;
       - **контрактов API**:
         - файлы контрактов в `.madspec/contracts/`;
         - основной файл контрактов `.madspec/contracts/openapi.yaml`, если используется REST API;
         - определения endpoints, запросов и ответов;
       - **моделей данных**:
         - схемы из `.madspec/data-model.md`.
     - Если такие файлы существуют, ссылайся на них явно в описании шага.

   - **Создай минимально достаточный набор стартовых шагов**:
     - Для простого проекта это обычно **один** шаг.
     - Для более сложного старта допускается несколько шагов, но только если без этого нельзя зафиксировать реальные зависимости или отдельные точки проверки.
     - Не начинай с абстрактной "базовой настройки проекта", если сразу можно запланировать функциональный шаг с понятным результатом.
     - Если для функции существуют связанные артефакты, включи ссылки на них в описание шага.
     - Для UI-шагов укажи в `description.md` и `planning-context.md`, какие screen prototypes, flow steps и входной экран являются acceptance contract.
     - Если `.madspec/<BRANCH>/deployment.md` существует, добавляй в `tasks.md`, `tests.md`, `validation.md` только те требования, которые действительно нужны для выбранного способа развертывания.

   - Инициализируй `.madspec/<BRANCH>/memory/progress.json`:
     - если файл не существует, создай его на основе шаблона `.madspec/templates/planning-state-template.json`;
     - убедись, что структура включает:
       - `plannedSteps: []` на верхнем уровне;
       - `planningMetadata` с полями `lastPlannedStep`, `planningPhase`, `stepDependencies`, `progressMetrics`;
     - установи `planningPhase: "initial"`;
     - инициализируй `progressMetrics`:
       - подсчитай общее количество функций `P1`, `P2`, `P3` из `concept.md`;
       - установи начальные значения: все функции непокрыты.
     - Если файл уже существует, **НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ НЕ ИЗМЕНЯЙ** значение `currentImplementStep`.

   - Не редактируй `planning-context-cache.md` и `implementation-plan.md` вручную как primary source: они пересобираются из structured memory.

   - Для каждого действительно нового шага:
     - создай директорию `.madspec/<BRANCH>/steps/step-[NN]-[name]/`;
     - используй формат номера `step-XX`, где `XX` — двузначное число с ведущим нулем;
     - используй `kebab-case` в имени шага, например `step-01-auth-foundation`;
     - создай файлы:
       - `description.md`;
       - `tasks.md`;
       - `tests.md`;
       - `validation.md`;
       - `planning-context.md`.
     - В `description.md` явно укажи `step kind` и `TDD policy`.
     - В `tests.md` для `code` шага обязательно создай секции `Red`, `Green`, `Relevant Suite`, `Manual Checks`; для `non-code` шага — `Manual Checks` и `Waiver`.
     - В `validation.md` для `code` шага обязательно добавь критерии: red зафиксирован, focused test green, relevant suite green после refactor, regression сохранена.
     - В `planning-context.md` зафиксируй:
       - почему этот шаг создан;
       - зависимости и покрываемые функции;
       - ключевые решения;
       - связанные артефакты;
       - размер и сложность шага.
     - Зарегистрируй шаг через `madspec memory register-step --stage mvp.plan --step-id step-[NN]-[name] --step-kind <code|non-code> --title "<заголовок>" --summary "<описание>" --covers <function> --related-artifact <path> --size <small|medium|large> --complexity <low|medium|high> ...`.
     - Для `non-code` шага обязательно передай `--tdd-policy waived --waiver-reason "<причина>"` или `--tdd-policy not-applicable`.
     - Команда должна автоматически обновить `plannedSteps`, `stepStatus`, `stepMetadata`, `coversFunctions`, `planningMetadata.stepDependencies`, `planningMetadata.lastPlannedStep` и `planningMetadata.progressMetrics`.

   - Отобрази визуализацию прогресса планирования, см. раздел 6.

3. **Режим Incremental (последующие запуски)**:

   - Загрузи только необходимый контекст:
     - `.madspec/<BRANCH>/concept.md` для понимания функций и приоритетов;
     - `policy_context` из `madspec memory retrieve --stage mvp.plan --toon-output`;
     - `.madspec/<BRANCH>/planning-context-cache.md` для понимания структуры, если кэш уже существует;
     - если кэш не существует, сначала загрузи `madspec memory retrieve --stage mvp.architecture --toon-output --full-artifact`, затем используй `architecture.md` и `data-model.md` как generated detail views;
     - если существует `.madspec/<BRANCH>/deployment.md`, загрузи его и учитывай ограничения развертывания;
     - `.madspec/<BRANCH>/implementation-plan.md` для понимания уже запланированных шагов;
     - список уже запланированных шагов из `progress.json`.

   - **Определи следующий минимально достаточный набор новых шагов** на основе:
     - зависимостей из `planningMetadata.stepDependencies`;
     - уже запланированных шагов из `plannedSteps`;
     - приоритетов из `concept.md`;
     - архитектуры и связанного контекста.

   - **Проверь наличие связанных артефактов**:
     - для UI-шагов — UI-дизайн, storyboard-прототипы, review journeys и входные экраны;
     - для API и интеграций — файлы контрактов в `.madspec/contracts/`;
     - для шагов, связанных с данными, — схемы из `.madspec/data-model.md`.
     - Если такие файлы существуют, включи ссылки на них в `description.md` и `tasks.md`.

   - **Создай минимально достаточный набор новых шагов**:
     - Для простой итерации это обычно **один** шаг.
     - Не создавай несколько шагов только потому, что работа затрагивает код, тесты, документацию и валидацию одновременно.
     - Несколько новых шагов допустимы только при реальных зависимостях, заметно разных рисках или явной просьбе пользователя.

   - Для каждого нового шага:
     - создай директорию `.madspec/<BRANCH>/steps/step-[NN]-[name]/`;
     - создай или обнови `description.md`, `tasks.md`, `tests.md`, `validation.md`, `planning-context.md`;
     - укажи `step kind`, `TDD policy`, покрываемые функции, зависимости и ссылки на связанные артефакты;
     - если существует `.madspec/<BRANCH>/deployment.md`, добавь только те требования, которые действительно нужны для выбранного способа развертывания.

   - Если стратегия еще не зафиксирована или изменилась, добавь ее через `madspec memory capture --stage mvp.plan ...`.
     - Не делай лишний `capture`, если `planOverview` уже достаточен и новый проход не меняет стратегию.

   - Для каждого кандидата выполни детерминированную проверку:
     - `madspec memory next-step --stage mvp.plan --candidate-step step-[NN]-[name] --depends-on <dep1> --depends-on <dep2>`
     - если команда завершилась с ошибкой, пересмотри имя шага и зависимости;
     - не добавляй шаг в `progress.json`, пока проверка не прошла успешно.

   - Зарегистрируй каждый принятый шаг через `madspec memory register-step`.

   - Когда весь набор новых шагов за текущий проход готов, выполни **один итоговый** `madspec memory checkpoint --stage mvp.plan --summary "<validated summary>"`.

4. **Определение следующего шага** (алгоритм выбора):

   - Найди все функции из `concept.md`, которые еще не покрыты запланированными шагами:
     - учитывай все функции: `P1`, `P2`, `P3`;
     - проверь, какие функции уже покрыты шагами из `plannedSteps`.

   - Для каждой непокрытой функции определи необходимые шаги на основе архитектуры и контекста, но объединяй связанные функции в один шаг, если их можно реализовать и проверить как единое изменение.

   - Выбирай шаги с учетом приоритета `P1 -> P2 -> P3`:
     - сначала планируются функции `P1`;
     - затем `P2`;
     - затем `P3`.
   - Приоритет определяет очередность покрытия, а не обязанность создавать отдельный шаг для каждой функции внутри одного приоритета.

   - Проверь, что зависимости шага уже запланированы:
     - проверь `planningMetadata.stepDependencies`;
     - убедись, что все зависимости присутствуют в `plannedSteps`.

   - Если все функции покрыты, но остались технические шаги:
     - планируй интеграцию, оптимизацию, рефакторинг или другие необходимые технические шаги;
     - учитывай зависимости от уже запланированных шагов.
   - Не создавай технический шаг только потому, что хочется начать с "подготовки", если тот же результат можно безопасно включить в функциональный шаг.

   - Не интерпретируй `P1/P2/P3` как обязательный сигнал разбивать работу на отдельный шаг для каждой функции.

5. **Создание структуры шага**:

   - Создай директорию `.madspec/<BRANCH>/steps/step-[NN]-[name]/`.
   - **Формат номера**: `step-XX`, где `XX` — двузначное число с ведущим нулем.
   - **Имя шага**: используй `kebab-case`.
   - Определи номер шага на основе количества уже запланированных шагов: `NN = plannedSteps.length + 1`, если не нужен другой номер для согласованности.

   - Создай файлы на основе шаблонов и контекста:
     - `description.md` — описание шага, что нужно сделать и почему шаг важен;
     - `tasks.md` — список конкретных задач;
     - `tests.md` — TDD артефакты (`Red`, `Green`, `Relevant Suite`, `Manual Checks`, `Waiver`);
     - `validation.md` — критерии успешного завершения, включая TDD gates;
     - `planning-context.md` — контекст планирования шага с ключевыми решениями.

   - В каждом файле укажи:
     - номер и название шага;
     - зависимости от других шагов;
     - приоритет функции, которую покрывает шаг, если он относится к функции из концепции;
     - связь с функциями из концепции;
     - ссылки на связанные артефакты, если применимо.

6. **Кэширование контекста**:

   - `planning-context-cache.md` является generated view и должен пересобираться из structured memory после `register-step` и `checkpoint`.
   - Не редактируй `.madspec/<BRANCH>/planning-context-cache.md` вручную как primary source.
   - В инкрементальном режиме используй кэш вместо полной загрузки generated `architecture.md`, если этого достаточно для выбора следующего шага.

7. **Визуализация прогресса планирования**:

   - После каждого завершенного прохода вычисляй и отображай:
     - процент покрытия функций `P1`;
     - процент покрытия функций `P2`;
     - процент покрытия функций `P3`;
     - общий прогресс планирования.

   - Формат отображения прогресса:
     ```
     Прогресс планирования:
     P1 функции: [X/Y] покрыты ([Z%]) ████████░░
     P2 функции: [X/Y] покрыты ([Z%]) ██████░░░░
     P3 функции: [X/Y] покрыты ([Z%]) ████░░░░░░
     Общий прогресс: [Z%]
     ```

   - Метрики прогресса хранятся в `planningMetadata.progressMetrics`.

8. **Валидация шага**:

   Перед сохранением файлов выполни валидацию текущего шага по следующему чек-листу:

   - [ ] Новый шаг имеет полное описание.
   - [ ] Новый шаг имеет задачи.
   - [ ] Новый шаг имеет тесты.
   - [ ] Новый шаг имеет критерии завершения.
   - [ ] Зависимости логичны и не создают цикл.
   - [ ] Шаг покрывает функцию из концепции или явный технический результат, необходимый для поставки.
   - [ ] Шаг ссылается на контракты и модели, если это применимо.
   - [ ] Шаг не слишком крупный и не слишком мелкий.
   - [ ] Шаг технически реализуем.

   Если валидация не пройдена:
   - укажи конкретные пункты, которые не выполнены;
   - предложи конкретные исправления;
   - **НЕ ПЕРЕХОДИ** к следующему шагу до прохождения валидации.

9. **Определение завершения планирования**:

   - После каждого прохода проверяй покрытие функций из концепции:
     - все ли функции `P1` покрыты запланированными шагами;
     - все ли функции `P2` покрыты запланированными шагами;
     - все ли функции `P3` покрыты запланированными шагами.

   - Используй метрики из `planningMetadata.progressMetrics` для проверки.

   - Если все функции покрыты:
     - проверь, остались ли технические шаги;
     - если все необходимые шаги уже запланированы, предложи перейти к `/madspec.mvp.implement`.

   - Если есть непокрытые функции:
     - покажи текущий прогресс планирования;
     - укажи, какие функции еще не покрыты;
     - предложи продолжить планирование только если это действительно нужно.

10. **Отчет**:
    - Выведи пути к созданным или обновленным файлам:
      - `.madspec/<BRANCH>/steps/step-[NN]-[name]/`;
      - `.madspec/<BRANCH>/steps/step-[NN]-[name]/planning-context.md`;
      - `.madspec/<BRANCH>/implementation-plan.md`;
      - `.madspec/<BRANCH>/memory/stages/mvp.plan.json`;
      - `.madspec/<BRANCH>/memory/progress.json`;
      - `.madspec/<BRANCH>/planning-context-cache.md`.

    - Покажи информацию о новом шаге:
      - номер и название;
      - краткое описание;
      - зависимости;
      - покрываемые функции.

    - Покажи текущий прогресс планирования:
      - количество запланированных шагов;
      - визуализацию прогресса;
      - упрощенный граф зависимостей, если это помогает понять структуру.

    - Если планирование завершено:
      - предложи перейти к `/madspec.mvp.implement`.
    - Если планирование не завершено:
      - покажи, какие функции еще не покрыты;
      - предложи следующий проход планирования только если он действительно нужен.

## Правила

- **СТРЕМИСЬ** к минимально достаточному числу шагов.
- **ОПРЕДЕЛЯЙ** зависимости явно.
- **ТРЕБУЙ** тесты для каждого шага.
- **ДОКУМЕНТИРУЙ** критерии завершения.
- **НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ НЕ ИЗМЕНЯЙ** `currentImplementStep` в `progress.json`.

## Структура шага

Каждый шаг должен содержать:
- **Номер и название**: `step-01-auth-foundation`, `step-02-profile-flow` и т.д.
- **Описание**: что делается на этом шаге.
- **Задачи**: конкретный список задач.
- **Тесты**: как проверить, что шаг выполнен правильно.
- **Валидация**: критерии успешного завершения.
- **Зависимости**: какие шаги должны быть завершены до этого.

## Выходные артефакты

- `.madspec/<BRANCH>/memory/stages/mvp.plan.json` — основной файл данных этапа plan;
- `.madspec/<BRANCH>/implementation-plan.md` — generated plan view;
- `.madspec/<BRANCH>/steps/step-[NN]-[name]/` — директория с описанием нового шага;
- `.madspec/<BRANCH>/steps/step-[NN]-[name]/planning-context.md` — контекст планирования шага;
- `.madspec/<BRANCH>/memory/progress.json` — файл отслеживания прогресса;
- `.madspec/<BRANCH>/planning-context-cache.md` — generated view кэша контекста планирования;
- `.madspec/<BRANCH>/project-context.md` — обновленный контекст проекта.

## Подсказки и помощь

### Контекстные подсказки

При ошибках валидации система может дать подсказки для создания плана реализации, но сначала опирайся на `gate_summary`, `policy_context` и канонические команды памяти.

## Следующий этап

- Если планирование завершено и все необходимые шаги уже зафиксированы:
  - переходи к `/madspec.mvp.implement` для начала реализации.
- Если планирование не завершено:
  - запускай следующий проход `/madspec.mvp.plan` только тогда, когда реально остались новые шаги или изменилась стратегия плана.
