## Пользовательский ввод

```text
$ARGUMENTS
```

## Обязательный skill `madspec-cli-operator`

- Перед началом работы обязательно найди и прочитай skill `madspec-cli-operator`.
- Дальше работай, опираясь на `madspec-cli-operator` как на базовый операционный навык для команд MADSpec CLI, артефактов `.madspec/` и контекста текущей ветки.

Ты **ОБЯЗАН** учитывать пользовательский ввод перед продолжением, если он не пустой.

## Сначала структурированная память

- Каноническое состояние этапа хранится в `.madspec/<BRANCH>/memory/stages/deploy.json`.
- Производный артефакт этапа: `.madspec/<BRANCH>/deployment.md`.
- Перед началом работы используй `madspec memory retrieve --stage deploy --toon-output`, если этот вывод читает агент.
- Из ответа `retrieve` обязательно прочитай `deploy_status`, `policy_context.required`, `policy_context.advisory` и `change_context`.
- Полное состояние этапа запрашивай только перед итоговой проверкой через `madspec memory retrieve --stage deploy --full-artifact --toon-output`.
- Для накопления подтвержденных сведений используй `madspec memory capture --stage deploy ...`.
- Для ратификации этапа используй `madspec memory checkpoint --stage deploy --summary ...`.
- После записи память пересобирается и проверяется через обычный цикл `consolidate + validate`.
- **ОБЯЗАТЕЛЬНО**: для вызовов `madspec memory capture` и `madspec memory checkpoint` используй `--from-file`. Записывай аргументы во временный JSON-файл в `.madspec/.tmp/` и передавай путь через `--from-file <path>`.

## Назначение команды

`madspec.deploy` помогает зафиксировать и уточнить способ развертывания для текущей ветки: окружения, единицы развертывания, конфигурацию, секреты, CI/CD, миграции, наблюдаемость, стратегию релиза и отката.

## Когда использовать

- как рекомендуемый этап после `/madspec.mvp.architecture` и перед `/madspec.mvp.plan`, если ограничения развертывания важны заранее;
- в feature-ветке, если изменения затрагивают инфраструктуру, конфигурацию, секреты, миграции, наблюдаемость или выпуск релиза;
- отдельно после завершения остальных стадий, если нужно оформить или уточнить реальный способ выкладки перед релизом;
- повторно, если после реализации изменились требования к окружениям, выкладке или откату.

## Предварительные условия

- должен быть доступен контекст текущей ветки через `madspec git current-branch`;
- репозиторий должен содержать хотя бы минимальный технический контекст;
- наличие `.madspec/<BRANCH>/tech-stack.md` и `.madspec/<BRANCH>/architecture.md` желательно, но их отсутствие не должно полностью блокировать работу;
- если данных недостаточно, не выдумывай недостающие решения: фиксируй ограничения и открытые вопросы.

## Правила диалога

- Сначала читай доступный контекст из памяти, артефактов и репозитория.
- Вопросы пользователю задавай только если важные сведения нельзя надежно восстановить из проекта.
- Задавай вопросы строго по одному.
- Не требуй повторного прохождения MVP- или feature-потока, если команда запускается отдельно после других стадий.

## Порядок работы

1. Определи текущую ветку через `madspec git current-branch`.
2. Выполни `madspec memory retrieve --stage deploy --toon-output`, если этот вывод читает агент.
3. Собери доступный контекст из репозитория и производных артефактов:
   - `.madspec/<BRANCH>/tech-stack.md`
   - `.madspec/<BRANCH>/architecture.md`
   - `.madspec/<BRANCH>/project-analysis.md`
   - `.madspec/<BRANCH>/feature-context.md`
   - `.madspec/<BRANCH>/implementation-plan.md`
   - `.madspec/<BRANCH>/review.md`
   - `.madspec/<BRANCH>/security-audit.md`
   - манифесты зависимостей, файлы CI, `Dockerfile`, `docker-compose*`, `helm`, `k8s`, `terraform` и похожие инфраструктурные файлы
4. Определи, что уже можно подтвердить:
   - цели развертывания;
   - окружения;
   - единицы развертывания и зависимости;
   - конфигурацию и секреты;
   - конвейер CI/CD;
   - миграции и резервное копирование;
   - наблюдаемость;
   - безопасность и доступ;
   - стратегию релиза и отката.
5. Если чего-то не хватает, задай пользователю один точный вопрос и после ответа продолжи.
6. Сохраняй подтвержденные сведения через `madspec memory capture --stage deploy`:
   - `--deploy-overview`
   - `--deploy-goal`
   - `--environment`
   - `--deployment-unit`
   - `--config-note`
   - `--secret-note`
   - `--cicd-trigger`
   - `--cicd-step`
   - `--release-artifact`
   - `--migration-note`
   - `--backup-note`
   - `--recovery-check`
   - `--observability-note`
   - `--security-control`
   - `--release-strategy`
   - `--rollback-strategy`
   - `--contract` для ограничений
   - `--next-action` и `--question`, если есть незакрытые пункты
7. После того как состояние стало достаточно полным, выполни `madspec memory checkpoint --stage deploy --summary "<итог>"`.
8. Убедись, что `.madspec/<BRANCH>/deployment.md` пересобран и отражает актуальное состояние.

## Важные правила

- `deployment.md` не редактируется вручную: это производное представление.
- Команда должна безопасно перезапускаться: повторный запуск уточняет уже накопленное состояние, а не ломает другие стадии.
- Если этап запускается после `review` или `security`, учитывай их выводы при уточнении окружений, секретов, наблюдаемости и стратегии отката.
- Если `deployment.md` уже существует, используй его как производное представление текущего состояния, но источником истины считай `deploy.json` и записи памяти.

## Что считается результатом

- `.madspec/<BRANCH>/memory/stages/deploy.json` содержит подтвержденное состояние этапа;
- `.madspec/<BRANCH>/deployment.md` пересобран из канонического состояния;
- `project-context.md` показывает актуальный статус этапа `deploy`;
- последующие команды `/madspec.mvp.plan`, `/madspec.feature.plan`, `/madspec.review` и `/madspec.security` могут опираться на этот артефакт.
