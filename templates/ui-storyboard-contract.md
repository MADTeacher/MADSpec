# UI Prototype Contract

Используй этот контракт как structural guide для `.madspec/<BRANCH>/ui-prototype/`.

Он задает обязательную структуру review-прототипа и требования к экранным HTML. Визуальный стиль контракт **не диктует** — он уникален для каждого проекта (см. `frontend-design` skill).

## Что обязательно должно быть в `index.html`

- Это обзорная страница review, а не каталог функций по приоритетам.
- Должен быть явно выделен `primary review flow`.
- Должен быть блок "С чего начать" с CTA на первый экран primary flow.
- Должен быть список review journeys с кратким описанием цели каждого сценария.
- Должна быть карта экранов и переходов, чтобы пользователь понимал, куда можно кликнуть дальше.
- Должны быть ссылки на все ключевые экраны, которые участвуют в review.
- Визуальный стиль `index.html` должен совпадать со стилем экранов приложения.

## Как должен выглядеть каждый экранный HTML-файл

Каждый `[screen].html` должен **выглядеть как реальный экран приложения** — не как описание того, что экран делает.

### Правильная структура экрана

```
[App nav-bar / header — настоящий элемент интерфейса приложения]
[Основной контент экрана с реальными UI-компонентами]
  — список с реалистичными mock-данными (имена, даты, числа)
  — форма с полями ввода и подписями
  — карточки с контентом по домену
  — игровое поле, дашборд, таблица — в зависимости от типа приложения
[Fixed review overlay в углу: ← Back | Home | Next →]
```

### Неправильная структура экрана

```
[Topbar с brand-mark и review-ссылками как главный элемент страницы]
[Карточки "UX-роль", "Primary CTA", "Обещание игроку" как основной контент]
[Описание того, что экран должен делать, вместо самого экрана]
```

### Review-навигация

Review-навигация (Back / Next / Home) — это **вспомогательный инструмент** для reviewer, а не часть UI приложения:

- Реализуй как `position: fixed` блок в углу экрана (например, правый нижний угол).
- Компактный: 3 небольшие ссылки/кнопки, без лишнего текста.
- Не должна занимать значимую часть экрана и вытеснять контент приложения.
- Стилизуй нейтрально или в тон дизайну, но она всегда вторична по отношению к основному UI.

Пример минимальной review-навигации:
```html
<nav class="review-nav-overlay">
  <a href="./prev-screen.html">← Back</a>
  <a href="./index.html">Home</a>
  <a href="./next-screen.html">Next →</a>
</nav>
```

```css
.review-nav-overlay {
  position: fixed;
  bottom: 20px;
  right: 20px;
  display: flex;
  gap: 8px;
  z-index: 9999;
  background: rgba(0,0,0,0.6);
  padding: 8px 12px;
  border-radius: 8px;
  font-size: 13px;
}
```

## Что обязательно должно быть в каждом экранном HTML-файле

- Настоящий UI этого экрана: nav-bar, контент, компоненты — в зависимости от типа экрана и домена.
- Реалистичный fake-контент: имена, числа, даты, названия товаров/задач/игроков — не "Пользователь 1" и не "Текст описания".
- Интерактивные состояния через vanilla JS там, где это необходимо для понимания механики экрана.
- Компактная review-навигация (Back / Next / Home) через `position: fixed`.

## Что запрещено в экранных HTML-файлах

- Карточки с мета-описанием экрана ("UX-роль", "Primary CTA", "Обещание игроку") как основной контент.
- Описание того, что экран "должен делать", вместо реализации этого экрана.
- Placeholder-текст ("Название элемента", "Описание", "Пользователь N") вместо реалистичных данных.
- Доминирующий topbar review-навигации, вытесняющий контент приложения.

## Требования к визуальному стилю

- Дизайн каждого проекта **уникален** — нельзя копировать стиль предыдущего прототипа.
- Шрифты — только Google Fonts, подключённые через `<link>`. Системные шрифты (Inter, Arial, Roboto) запрещены как единственный выбор.
- CSS-переменные используются для консистентности палитры внутри одного проекта.
- Визуальный стиль должен соответствовать домену проекта (игра, финансы, здоровье, e-commerce — каждый имеет свой характер).

## Storyboard rules

- Primary journey должен быть кликабелен от `index.html` до финального экрана сценария.
- Если в concept есть authentication, onboarding, verification или другой access gate, review-flow по умолчанию начинается с него.
- Если auth/onboarding нет, начни с первого main-task flow, который решает ключевую пользовательскую задачу.
- Альтернативные пути допустимы, но основной сценарий не должен требовать ручного редактирования URL.
- Каждый экран должен поддерживать понятный возврат назад и переход к следующему шагу сценария через review overlay.

## Review expectations

- Пользователь должен иметь возможность открыть `index.html`, пройти ключевой сценарий по кликам и оставить feedback по экрану или переходу.
- Прототип не обязан содержать реальную бизнес-логику или интеграции.
- Прототип обязан визуально и навигационно отражать согласованный user journey.
- Каждый экран должен выглядеть так, будто это скриншот готового приложения, а не схема для разработчика.
