# Дорожная Карта Полного Перехода На Этап Phase 2

Этот документ описывает следующие шаги после Epic 10 для полного перехода от opt-in режима к этапу Phase 2, включенному по умолчанию.

## Текущее Состояние

Этап Phase 2 уже существует в кодовой базе, но пока работает только как opt-in режим.

- Конфигурация нового проекта по умолчанию содержит `parallelRuntime.phase1Enabled=true` и `parallelRuntime.phase2Enabled=false`.
- Команды `madspec memory tasks ...`, `work-items ...`, `proposals ...` и `coordinator explain` остаются видимыми в командном интерфейсе.
- При выключенном `phase2Enabled` они возвращают явный отказ с `reason="phase2_disabled"`.
- Сценарии с одним агентом и сценарии Phase 1 остаются основным режимом и не требуют ручной миграции.

## Что Должно Быть Закрыто До Перехода На Режим По Умолчанию

- Набор регрессионных проверок для двух режимов должен стабильно покрывать и режим Phase 1 по умолчанию, и opt-in режим для Phase 2.
- Операторские инструкции в `docs/cli/`, `README.md` и `skills/madspec-cli-operator/` должны быть согласованы и не содержать противоречий по политике выката.
- Практическая обкатка на opt-in проектах должна показать, что поток работы через proposals и coordinator не создает скрытых регрессий в сценариях планирования и реализации.
- Проверка готовности релиза должна включать отдельный сигнал по Phase 2, а не только общий зеленый статус тестов.
- Диагностика через `doctor`, `timeline`, `conflicts` и `agents subagents context` должна оставаться понятной и в режиме по умолчанию, и в opt-in режиме.

## Критерии Готовности Перед Переключением По Умолчанию

- Обязательный поднабор регрессионных тестов для режима Phase 1 по умолчанию стабильно зеленый.
- Обязательный поднабор регрессионных тестов для opt-in режима Phase 2 стабильно зеленый.
- `agents subagents context` ведет себя предсказуемо в обоих режимах.
- Прямые записи из захваченного сеанса переводятся на proposal-протокол только тогда, когда включен Phase 2.
- Документация явно объясняет поведение переключателя, правила миграции и операторские действия.
- Контрольный список перед релизом подтверждает, что режим `phase2Enabled=true` проверен на текущем кандидате релиза CLI.

## Переходная Семантика, Которую Потом Можно Будет Удалить

- Переходные формулировки о том, что Phase 2 работает только как opt-in режим.
- Явный отказ времени выполнения `reason="phase2_disabled"` для семейств coordinator-команд.
- Необходимость отдельно объяснять поведение двух режимов в операторском навыке.
- Часть пояснений о совместимости вокруг Phase 1 как единственного режима по умолчанию, если постоянное включение Phase 2 подтвердит стабильность.
- Возможность документировать `phase1Enabled` только как временный флаг совместимости, если позже Phase 1 и Phase 2 будут сведены в единый стабильный протокол.

## Последовательность Полного Перехода

1. Расширить CI до стабильного набора проверок для двух режимов и зафиксировать обязательные поднаборы тестов для каждого режима.
2. Довести до стабильного состояния операторские инструкции, руководство по устранению проблем и проверки точности документации.
3. Провести практическую обкатку на opt-in проектах и собрать повторяемые результаты по потоку работы через proposals и coordinator.
4. Собрать отдельный сигнал готовности релиза по итогам обкатки и регрессионных тестов.
5. Перевести значение `parallelRuntime.phase2Enabled` в `true` по умолчанию для новых проектов.
6. После дополнительного стабильного периода убрать переключатель и переходные формулировки из документации, навыка и подсказок CLI.

## Критерии Продолжения Или Остановки

Ниже перечислены stop/go criteria для полного перехода на постоянно включенный Phase 2.

`Go`:

- нет открытых регрессий уровня P1 или P2 в runtime Phase 2;
- набор проверок для двух режимов стабильно зеленый;
- операторская документация и руководство по устранению проблем отражают фактическое поведение CLI;
- практическая обкатка подтверждает, что поток работы через proposals и coordinator не создает непредсказуемых блокировок в реальных сценариях.

`Stop`:

- Phase 2 ломает ожидания операторов в режиме по умолчанию или создает скрытые регрессии в `mvp.plan` и `mvp.implement`;
- диагностический слой не может уверенно объяснить состояния blocked, conflict и результаты работы coordinator;
- перед релизом нет отдельного сигнала, что opt-in сценарии действительно прогнаны;
- rollout требует разрушительной миграции существующих структур `.madspec` или ручного переписывания старых session flows.
