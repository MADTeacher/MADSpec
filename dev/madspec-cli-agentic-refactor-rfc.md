# RFC: Упрощение Архитектуры `madspec_cli` Для Агентной Разработки

> Статус: архивный документ. RFC реализован как серия завершённых PR; файл оставлен для исторического контекста и объяснения принятых решений.

## 1. Зачем Нужен Этот Документ

Этот RFC дополняет существующие дорожные карты в `dev/` и фокусируется на отдельной задаче: сделать кодовую базу `madspec_cli` проще для чтения, безопаснее для локальных изменений и удобнее для работы LLM-агентов.

Основание для RFC:

- в кодовой базе остаются очень крупные модули и классы;
- низкоуровневые утилиты местами содержат скрытую бизнес-логику и побочные эффекты;
- часть правил реализована дважды в разных слоях;
- по названию модуля не всегда понятно, где заканчивается ответственность слоя;
- агенту трудно определить безопасную точку входа для изменения без чтения большого объёма несвязанных деталей.

Документ задаёт целевую форму рефакторинга, порядок внедрения и критерии готовности. Он не заменяет существующие roadmaps по `memory`, а даёт более прикладной план по упрощению структуры всей кодовой базы CLI.

## 2. Что Считаем Главной Проблемой

На текущий момент основное сопротивление для сопровождения создают не отдельные дефекты, а форма кода:

1. Границы слоёв не всегда очевидны и местами нарушаются.
2. В нескольких местах один модуль совмещает хранение, orchestration, рендеринг и синхронизацию.
3. Часть правил существует в двух независимых реализациях.
4. Крупные файлы затрудняют поиск безопасной точки изменения.
5. Публичная поверхность пакетов размыта из-за фасадных реэкспортов и экспорта внутренних helper-функций.

Для агентной работы это особенно дорого:

- увеличивается объём контекста перед любым изменением;
- сложнее понять, какие импорты безопасны;
- повышается риск непредвиденного побочного эффекта;
- мелкие исправления чаще требуют чтения нескольких больших модулей сразу.

## 3. Цели

### Основные цели

1. Восстановить понятные архитектурные границы между `shared`, `features`, `memory`, `application`, `domain`, `infrastructure`.
2. Сузить ответственность крупных модулей и разрезать самые перегруженные файлы.
3. Убрать скрытые побочные эффекты из низкоуровневых helper-ов.
4. Сделать правила workflow едиными и повторно используемыми.
5. Сформировать стабильные и понятные точки входа для агентных изменений.

### Не цели

1. Полная перепись всего `memory` за один цикл.
2. Введение тяжёлого контейнера зависимостей.
3. Редизайн CLI-контрактов без необходимости.
4. Изменение пользовательских workflow только ради “чистой” архитектуры.

## 4. Архитектурные Правила После Рефакторинга

### 4.1 Направление зависимостей

- `domain` зависит только от стандартной библиотеки, собственных моделей и доменных helper-ов.
- `application` координирует сценарии и зависит от `domain` и узких портов.
- `infrastructure` реализует порты, хранение и интеграции.
- `cli` только адаптирует ввод-вывод и вызывает application use case.
- `shared` не импортирует конкретные `features` и не знает про частные workflow-сценарии.

### 4.2 Правило низкоуровневого helper-а

Если функция называется как утилита хранения или сериализации, она не должна:

- запускать синхронизацию в другой store;
- пересчитывать проекции;
- разрешать ветку через git;
- принимать решение бизнес-уровня.

Такие переходы должны жить в application-service или orchestrator-модуле.

### 4.3 Правило валидации

Каждое бизнес-правило существует в одном месте:

- либо как доменный validator;
- либо как application validator;
- но не как две независимые реализации для `gates` и для реального workflow.

## 6. Главные Объекты Рефакторинга

### 6.1 `memory/shared/system_store/store.py`

Сейчас это центральный перегруженный объект. Целевое состояние:

- один слой отвечает за подключение, транзакции и schema lifecycle;
- отдельные store-классы отвечают за свои bounded contexts;
- orchestration нескольких store живёт выше.

Предлагаемое разбиение:

- `db.py`: соединение, миграции, транзакции, базовые cursor helpers;
- `runtime_store.py`: runtime state, snapshots, sessions;
- `task_store.py`: tasks, work items, claims, leases;
- `artifact_store.py`: artifacts, materialized records, artifact search metadata;
- `proposal_store.py`: merge/runtime proposals и history;
- `index_store.py`: indexing state, retrieval logs, статусы и служебные таблицы.

### 6.2 `features/policy/infrastructure/storage.py`

Нужно разделить минимум на:

- `repository.py`: чтение и запись состояния;
- `normalizers.py`: нормализация входных структур;
- `renderers.py`: markdown/plain-text output;
- `sync.py`: синхронизация в memory/system store;
- `history.py` или `proposals.py`: proposal/history persistence, если объём останется большим.

### 6.3 `features/change/infrastructure/storage.py`

Нужно разделить минимум на:

- `repository.py`: JSON/JSONL state;
- `baseline.py`: baseline capture;
- `diffing.py`: git diff и derived change context;
- `renderers.py`: markdown export;
- `sync.py`: публикация в memory/artifact store.

### 6.4 `memory/semantic/*`

Сейчас проблема не только в размере файлов, но и в форме API.

Нужно перейти от длинных функций с десятками аргументов к payload-объектам:

- `ConceptCapturePayload`
- `DesignCapturePayload`
- `TechCapturePayload`
- `ArchitectureCapturePayload`
- `FeatureInitCapturePayload`
- `DeployCapturePayload`

И отдельно держать:

- валидацию области capture;
- построение fact records;
- построение decision records;
- stage-specific parsing.

### 6.5 `features/init/cli.py`

Нужно оставить тонкий CLI-фасад и вынести:

- `arg_resolution.py`
- `interactive_selection.py`
- `progress_reporting.py`
- `post_init_guidance.py`
- `runner.py` или `orchestrator.py`

Это уменьшит размер команды и позволит агенту менять, например, только post-init UX без риска задеть инициализацию проекта.

## 7. Целевая Последовательность PR

Ниже план не на один коммит, а на серию безопасных маленьких PR.

### PR 1. Убрать скрытые побочные эффекты и восстановить слой orchestration

**Цель:** сделать низкоуровневые helper-ы предсказуемыми.

**Шаги:**

1. Перенести синхронизацию system store из `write_json()` и `append_jsonl()` в явные application-service вызовы.
2. Убедиться, что helper-ы хранения занимаются только файловым I/O.
3. Убрать feature-зависимости из `shared`, где они ещё остаются, через явную передачу resolved branch / policy results / callback-портов.

**Критерий готовности:**

- `shared` не импортирует `features.*`;
- запись в JSON больше не вызывает неявную синхронизацию в другой store;
- сценарии, которым нужна синхронизация, делают это явно.

### PR 2. Единый движок workflow-валидации

**Цель:** убрать расхождение между gate evaluation и реальным workflow.

**Шаги:**

1. Выделить validator для `register-step`.
2. Выделить validator для `checkpoint-step`.
3. Выделить validator для `complete-step`.
4. Сделать `features/gates` тонким адаптером над этими validator-ами.

**Критерий готовности:**

- правила шага не закодированы дважды;
- gate result и реальная команда используют один источник истины;
- добавлены контрактные тесты на совпадение поведения.

### PR 3. Разделить `MemoryStore` по bounded contexts

**Цель:** устранить главный god object.

**Шаги:**

1. Выделить общий `db.py`.
2. Вынести из `MemoryStore` по одному куску ответственности за PR.
3. На переходный период оставить совместимый фасад `MemoryStore`, который делегирует в новые store-классы.

**Критерий готовности:**

- файл `store.py` перестаёт быть основным местом для всей логики;
- новые store-модули имеют узкую ответственность;
- можно менять работу с artifacts, не читая код задач и proposals.

### PR 4. Разрезать oversized infrastructure-модули `policy` и `change`

**Цель:** привести название модулей в соответствие с обязанностями.

**Шаги:**

1. Разделить `policy/infrastructure/storage.py`.
2. Разделить `change/infrastructure/storage.py`.
3. Оставить переходный фасад только при необходимости и только временно.

**Критерий готовности:**

- новый разработчик может определить место изменения по имени файла;
- markdown rendering, state persistence и sync перестают жить в одном модуле;
- уменьшается размер каждого файла и число “случайных” импортов.

### PR 5. Сузить API semantic capture

**Цель:** сделать семантический слой пригодным для локальных и агентных изменений.

**Шаги:**

1. Ввести payload-объекты по стадиям.
2. Разделить `records.py` по типам записей или по стадиям.
3. Разделить `validate_capture_scope()` на stage-specific validators.
4. Сократить число keyword-параметров в публичных функциях.

**Критерий готовности:**

- публичные функции semantic capture больше не принимают десятки разрозненных аргументов;
- stage-specific логика читается отдельно;
- агент может работать с одной стадией без чтения всего capture pipeline.

### PR 6. Упростить CLI-адаптеры и уменьшить размер команд

**Цель:** сделать CLI-поверхность тонкой и единообразной.

**Шаги:**

1. Вынести повторяющийся шаблон `parse -> use case -> emit -> error mapping`.
2. Разделить `features/init/cli.py`.
3. Сократить boilerplate в `agents`, `policy`, `change`, `gates`, где это даст выигрыш без усложнения абстракций.

**Критерий готовности:**

- CLI-модуль остаётся точкой адаптации, а не местом накопления логики;
- крупные команды можно читать независимо от UI-деталей;
- ошибка форматирования вывода не требует чтения orchestration-кода.

### PR 7. Ужесточить публичную поверхность пакетов

**Цель:** упростить навигацию и снизить риск импорта внутренних деталей.

**Шаги:**

1. Убрать экспорт внутренних helper-ов из `memory/__init__.py`.
2. Минимизировать фасадные re-export модули.
3. Добавить package-level описание стабильных entry points для крупных подсистем.

**Критерий готовности:**

- ownership модуля понятен по пути импорта;
- внутренние символы не выглядят как часть публичного API;
- агенту проще выбрать корректную точку расширения.

## 8. Предлагаемые Правила Для Новых Изменений

До завершения рефакторинга полезно ввести временные правила:

1. Не добавлять новые feature-импорты в `shared`.
2. Не добавлять новые скрытые побочные эффекты в файловые helper-ы.
3. Не дублировать validator, если правило уже существует в workflow.
4. Не расширять `storage.py`, если изменение логически относится к `renderers`, `normalizers` или `sync`.
5. Если функция требует больше 8-10 параметров доменного уровня, сначала проверить, не нужен ли payload-объект.

## 9. Как Это Упростит Работу Агентов

После выполнения этого RFC агенту станет проще:

- локализовать ответственность по имени пути;
- безопасно читать только один bounded context вместо супермодуля;
- добавлять правило в одном месте без риска забыть дублирующую реализацию;
- менять CLI-вывод без погружения в бизнес-логику;
- строить частичный контекст по задаче, а не загружать половину подсистемы.

Практический эффект:

- меньше токенов на разогрев контекста;
- меньше шанс затронуть несвязанное поведение;
- проще делегировать работу нескольким агентам по непересекающимся файлам;
- легче писать точечные тесты и ревьюить патчи.

## 10. Метрики Успеха

Рефакторинг считается успешным, если выполняются наблюдаемые условия:

1. В `shared` отсутствуют импорты из `features`.
2. Файлы-кандидаты на разбиение уменьшаются до разумного объёма и узкой ответственности.
3. Для `register-step`, `checkpoint-step`, `complete-step` существует единый источник бизнес-правил.
4. `MemoryStore` перестаёт быть единственной точкой доступа ко всем типам данных.
5. Публичные API `memory` и `features/*/infrastructure` становятся заметно уже и понятнее.
6. Типичное изменение по одной подсистеме требует чтения меньшего числа файлов.

## 11. Рекомендуемый Порядок Внедрения

Если делать в несколько волн, оптимальный порядок такой:

1. PR 1
2. PR 2
3. PR 3
4. PR 4
5. PR 5
6. PR 6
7. PR 7

Причина порядка:

- сначала убираем самые опасные скрытые связи;
- затем фиксируем единый источник правил;
- потом разрезаем крупные узлы;
- и только после этого шлифуем CLI-фасады и публичные API.
