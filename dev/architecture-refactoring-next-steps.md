# Следующие шаги рефакторинга архитектурных границ

> Статус: архивный документ. Этот план второй волны сохранён как исторический follow-up после завершённого цикла рефакторинга и не считается активным backlog-документом.

Документ продолжает [architecture-boundaries-roadmap.md](./architecture-boundaries-roadmap.md): фиксирует **что ещё можно сделать**, в каком порядке и с какими критериями готовности.

## 1. Контекст

После первого цикла рефакторинга:

- домен и основные направления зависимостей приведены в порядок;
- остались **частично закрытые** пункты **2.1**, **3.1** и **не начатый** пункт **3.2**;
- часть связей по-прежнему реализована через **ленивые импорты** вместо явной композиции в корне приложения.

Этот файл — **дорожная карта второй волны**, а не обязательный бэклог на один релиз.

## 2. Цели и ограничения

### Цели

1. Убрать оставшуюся жёсткую связь **`memory/shared/validation_views.py` → `stages/*`** за счёт уже существующего реестра стадий (или его расширения).
2. По желанию — унифицировать доступ к **git-операциям** через контракт из `shared/kernel/ports.py` и точку композиции (корень CLI / orchestrator).
3. По желанию — вынести **общие JSON-утилиты** из `memory/shared/storage.py` в `shared/infra/`, оставив в memory только пути и логику, специфичную для `.madspec`.

### Не цели (на эту волну)

- Полная перепись `memory/semantic` и `memory/projection` (отдельное решение уровня эпика).
- Введение контейнера зависимостей или фреймворка DI.
- Изменение пользовательского контракта CLI без необходимости.

## 3. Эпики и порядок

Рекомендуемый порядок учитывает **зависимости** и **риск регрессий**.

| Порядок | Эпик | Зависимости | Риск |
|---------|------|-------------|------|
| A | Реестр стадий и `validation_views` | Уже есть `memory/shared/stage_registry.py` | Средний |
| B | JSON-утилиты в `shared/infra` | Нет жёстких зависимостей от A | Низкий–средний (много файлов) |
| C | Git-порт и композиция | Желательно после стабилизации A или B | Средний |
| D | Углубление изоляции `features` (по желанию) | Нет | Низкий по объёму, спорный по пользе |

Эпики **A** и **B** можно вести **параллельно** разными людьми, если не трогать одни и те же строки в одном коммите.

## Эпик A — Завершить фазу 2.1: `validation_views` без прямых импортов `stages/*`

### Проблема

`memory/shared/validation_views.py` импортирует загрузчики, валидаторы и рендереры из каждого `memory/stages/*/state.py`. Это нарушает целевое правило: **общий слой `memory/shared` не зависит от конкретных стадий на уровне импорта модуля**.

В `stage_registry.py` уже заложены регистрации (в т.ч. загрузчики, валидаторы, рендереры) при импорте пакета `memory/stages`.

### Предлагаемые шаги

1. **Инвентаризация:** составить таблицу «вызов в `validation_views` → символ из `stages`» и сопоставить с тем, что уже регистрируется в `stage_registry` (добавить недостающие ключи при необходимости).
2. **Расширение API реестра (если нужно):** единый способ получить по ключу стадии:
   - `load_state(path)` / `schema_errors(raw)` / `reference_errors(...)` / `render_*` — в зависимости от того, что реально использует `validate_generated_stage_views`.
3. **Пошаговая замена:** заменить блоки `if "mvp.concept" in scope...` на обращения к реестру, сохраняя поведение и тексты ошибок.
4. **Проверка:** прогон тестов + ручной сценарий `madspec memory consolidate` и команда, которая дергает валидацию представлений (например, путь через `doctor` / `validate`, в зависимости от проекта).

### Критерий готовности

- В `validation_views.py` **нет** `from ..stages.`.
- Импорт пакета `memory.stages` по-прежнему инициализирует реестр (как сейчас для `canonical_state`).
- Регрессий в сообщениях об ошибках валидации нет (или зафиксированы намеренные уточнения в CHANGELOG при необходимости).

### Риски

- Реестр может не покрыть все комбинации «стадия + вид + вспомогательные функции» (`is_empty_*`, `uncovered_*`) — потребуется **дополнительная регистрация** или тонкие фасады в одном месте.

## Эпик B — Фаза 3.2: общие JSON-утилиты в `shared/infra`

### Проблема

Функции вроде `read_json`, `write_json`, `now_iso`, `append_jsonl` живут в `memory/shared/storage.py` и импортируются из **features** и **memory**. Это смешивает **общий I/O** и **раскладку памяти ветки**.

### Предлагаемые шаги

1. Создать `madspec_cli/shared/infra/json_storage.py` (или `json_io.py`) с чистыми функциями без знания о `.madspec`.
2. Оставить в `memory/shared/storage.py`:
   - `get_memory_paths`, `_default_progress_state`, всё, что завязано на структуру каталогов памяти;
   - тонкие реэкспорты из `shared/infra/...` на переходный период (по желанию).
3. Массово обновить импорты: сначала **внутри `memory/`**, затем **`features/`**, затем тесты.
4. Удалить реэкспорты-фасады после стабилизации.

### Критерий готовности

- `memory/shared/storage.py` не содержит универсальных `read_json`/`write_json` без привязки к домену памяти **или** явно делегирует их в `shared/infra` без дублирования логики.
- Нет циклических импортов; `uv run pytest` (или принятый в проекте способ) зелёный.

### Риски

- Большое число файлов — лучше **несколько мелких коммитов** (например, сначала только `memory/`, потом `features/`).

## Эпик C — Фаза 3.1 (продолжение): единая точка для git

### Проблема

Протокол `CurrentBranchResolver` (и при необходимости расширения) объявлен в `shared/kernel/ports.py`, но вызовы `get_current_branch` / `is_git_repo` по-прежнему разбросаны с **ленивыми импортами** из `features.git.infrastructure.operations`.

### Предлагаемые шаги

1. Зафиксировать **минимальный контракт**: `get_current_branch`, `is_git_repo`, при необходимости `init_git_repo` — только то, что реально нужно снаружи `features/git`.
2. Ввести **одну фабрику** или **dataclass с коллбэками** в модуле композиции (например, `app.py` или узкий `madspec_cli/composition.py`), без обязательной передачи через все слои сразу.
3. Мигрировать **по одному вертикальному срезу**: сначала `memory/application/resolve_branch.py`, затем `change`, затем `init`, и т.д.
4. Тесты: подмена порта заглушкой без subprocess/git.

### Критерий готовности

- Выбранные модули **не** содержат `from madspec_cli.features.git...` даже внутри функций (или их число существенно сокращено и задокументировано как исключение).
- Поведение CLI не меняется для пользователя.

### Риски

- Избыточная абстракция — останавливаться, когда **тестируемость** и **читаемость** выигрывают, а не «везде протокол».

## Эпик D — По желанию: меньше ленивых импортов между `features`

### Проблема

Между `features/*` нет импортов в заголовках файлов, но **внутри функций** остаются ленивые импорты (`init`, `subagent_context`, `change/storage`, и т.д.).

### Варианты

1. **Оставить как есть** — приемлемо, если команда считает `init` композиционным корнем.
2. **Вынести оркестрацию** в один модуль `features/composition/` или в корневой слой, а use-case’ы принимать **уже готовые** коллбэки/сервисы в конструкторе или параметрах (без импорта соседних features).

### Критерий готовности

- Согласованное правило в `AGENTS.md` или в этом репозитории: *когда ленивый импорт допустим, когда нет*.

## 4. Рекомендуемая последовательность спринтов

| Спринт | Содержание | Ожидаемый результат |
|--------|------------|---------------------|
| 1 | Эпик A (MVP): убрать импорты `stages` из `validation_views`, покрыть текущие пути валидации | Критерий A выполнен |
| 2 | Эпик B: перенос JSON-утилит + обновление импортов пакетами | Меньше смешения memory и общего I/O |
| 3 | Эпик C: 1–2 критичных входа (например `resolve_branch` + один feature) | Доказанный паттерн порта без полной миграции |
| 4 | Эпик C (продолжение) или D | По необходимости |

## 5. Проверки после каждого шага

- `madspec --help`, затем затронутые подкоманды.
- Тесты: минимум затронутых модулей + полный прогон перед слиянием в основную ветку.
- Для изменений в памяти: `madspec memory doctor` (или эквивалент из документации проекта).
